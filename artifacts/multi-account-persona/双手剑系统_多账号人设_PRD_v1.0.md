# 双手剑系统「多账号人设」功能 PRD v1.0

## 1. 文档信息

- 产品：双手剑系统·面霸君版
- 模块：小红书内容工厂
- 版本：v1.0
- 日期：2026-07-30
- 实施基线：`0d72714`
- 功能基线：`1f2c883`
- 明确排除：不得带入 `f2b85a2` 及其后的“统一推荐标题排序”产品改动

## 2. 背景与问题

当前系统的数据层级实际为：

```text
业务定位
→ 商家 / 买家 / 专家视角
→ 单一人设
→ 选题、正文、发布、复盘
```

系统虽然已经使用 `GrowthAccount.id` 关联计划、选题、正文和复盘，但工作台会按照“用户＋业务＋视角”自动读取最新一条 `GrowthAccount`，导致同一视角只能稳定使用一个人设。

实际运营需要在同一视角下经营多个小红书账号。例如：

```text
留学生求职辅导
└─ 买家视角
   ├─ 留学生本人号
   └─ 留学生家长号
```

两个人设服务同一业务、同属买家视角，但目标用户、说话身份、内容素材、标题历史、正文和复盘必须彼此隔离。

## 3. 产品目标

### 3.1 核心目标

允许同一“业务定位＋视角”下创建和管理多个账号人设，并让每个账号人设独立拥有：

- 人设资料；
- 平台账号绑定；
- 来源使用记录；
- 选题和标题历史；
- 正文与发布记录；
- 三日复盘与方法学习数据。

### 3.2 用户价值

- 一个操作者可以管理多个内容账号，不必重复注册系统账号；
- 留学生本人、留学生家长等不同身份不会串内容；
- 每个账号能形成独立的标题记忆、正文语气和复盘结论；
- 历史数据无需重建，可以平滑进入多账号模式。

### 3.3 成功标准

- 同一视角可以创建至少两个账号人设；
- 切换账号人设后，人设、标题、正文和复盘100%隔离；
- 历史账号和历史内容不丢失；
- 页面初次加载速度不因账号人设数量增加而明显下降；
- 复盘Excel不会绑定到错误账号。

## 4. 非目标

本期不做：

- 小红书账号密码保存；
- 小红书自动登录或自动发布；
- 一个账号人设同时绑定多个小红书账号；
- 多平台统一发布；
- 多人协同编辑和审批流；
- 跨账号自动复制正文；
- `f2b85a2` 的统一标题推荐与排序功能。

## 5. 核心概念

### 5.1 业务定位

现有两条业务：

- 留学生求职辅导；
- 中高管职业决策。

业务母定位由同一业务下的所有视角和账号人设共享。

### 5.2 内容视角

继续使用现有三种全局视角：

- 商家；
- 买家；
- 专家。

代码中的 `GrowthPersona` 暂时继续表示内容视角，避免破坏历史数据和大量既有逻辑。

### 5.3 账号人设

账号人设是当前 `GrowthAccount` 的产品化名称。

一个账号人设包含：

- 人设名称；
- 一句话人设；
- 目标人群；
- 核心问题；
- 持续提供的价值；
- 信任来源；
- 语气和专属字段；
- 绑定的平台账号；
- 独立的内容生产与复盘数据。

### 5.4 平台账号绑定

平台账号是账号人设关联的小红书账号标识，只保存：

- 平台：小红书；
- 账号显示名称；
- 小红书号或账号ID；
- 主页链接，可选；
- 绑定状态。

系统不得保存平台密码、Cookie或登录凭据。

首版保持：

```text
一个激活的账号人设 ↔ 一个小红书账号
```

## 6. 新的信息架构

主流程保持0—5六步：

```text
0 业务定位
1 商家 / 买家 / 专家视角
2 账号人设
3 选题
4 正文
5 三日复盘
```

账号层级变为：

```text
业务定位
→ 内容视角
→ 账号人设
→ 来源、选题、正文、发布、复盘
```

示例：

```text
留学生求职辅导
└─ 买家视角
   ├─ 留学生本人号
   │  └─ 人设A、标题历史A、正文A、复盘A
   ├─ 留学生家长号
   │  └─ 人设B、标题历史B、正文B、复盘B
   └─ ＋新建账号人设
```

## 7. 页面与交互

### 7.1 全局上下文提示

页面顶部持续显示：

```text
留学生求职辅导 · 买家 · 留学生家长号
```

未选择账号人设时显示：

```text
留学生求职辅导 · 买家 · 待选择账号人设
```

未选择账号人设时：

- 可查看业务定位和三种视角；
- 不允许进入选题、正文和复盘；
- 页面明确提示“请先选择或创建账号人设”。

### 7.2 第2步改为“账号人设”

原“人设”模块改名为“账号人设”。

页面分为两层：

#### 第一层：账号人设选择

卡片展示：

- 人设名称；
- 平台账号名称；
- 一句话人设；
- 当前状态：已绑定、未绑定、已归档；
- 最近使用时间；
- 当前账号标记。

操作：

- 选择人设；
- 新建账号人设；
- 编辑；
- 复制现有人设，可放P1；
- 归档；
- 查看历史内容。

#### 第二层：当前人设详情

选择账号人设后，沿用现有人设字段：

- 一句话人设；
- 目标人群；
- 核心问题；
- 持续提供的价值；
- 信任来源；
- 视角专属字段；
- 高级业务事实；
- 只读历史方向；
- 平台账号绑定信息。

### 7.3 新建账号人设

入口：

```text
＋新建账号人设
```

创建方式：

1. 系统生成；
2. 手动填写；
3. 复制当前人设后修改，P1。

必填字段：

- 人设名称；
- 目标人群；
- 核心问题；
- 账号价值；
- 信任来源。

平台账号绑定首版允许稍后补充，不阻止选题和正文生成，但未绑定账号不能上传正式三日复盘Excel。

### 7.4 切换账号人设

切换时：

- 保存当前人设的已持久化数据；
- 清空未保存的标题编辑、正文选择和复盘表单临时状态；
- 如果存在未保存修改，弹出确认：

```text
当前账号人设有未保存修改。保存后切换，还是放弃修改？
```

选项：

- 保存并切换；
- 放弃并切换；
- 取消。

系统记住每个“用户＋业务＋视角”最后使用的账号人设。

刷新页面后优先恢复最后使用的人设；若人设已归档，则选择默认人设。

### 7.5 归档与删除

不提供物理删除。

归档后：

- 不出现在默认账号人设列表；
- 不参与新内容生产；
- 历史标题、正文和复盘继续可读；
- 可以恢复；
- 不计入激活人设数量。

如果账号人设存在已发布内容，归档前明确提示历史数据不会删除。

## 8. 选题与标题规则

### 8.1 方法适配

13种方法的默认、探索、禁用矩阵继续由内容视角决定，不因账号人设变化而改变。

例如：

- “留学生本人号”和“留学生家长号”都属于买家视角；
- 两者使用同一套买家方法适配矩阵；
- 但生成语境、标题历史和正文身份完全不同。

### 8.2 账号人设隔离

以下数据必须按 `account_id` 隔离：

- 标题批次；
- 已出现标题；
- 标题主题和语义去重历史；
- 已选标题；
- 正文承诺；
- 正文草稿；
- 发布和复盘记录。

### 8.3 跨人设重复

两层规则：

- 同一账号人设内：标题和主题执行硬去重；
- 同一视角的其他账号人设：只做相似提醒，不阻止生成。

原因：留学生本人和留学生家长可能讨论同一求职节点，但身份、冲突和表达方式不同。

### 8.4 对标来源

P0：

- 继续允许来源随 `GrowthAccount` 保存；
- 每个账号人设独立记录使用次数和迁移历史。

P1：

- 建立“业务＋视角”共享来源池；
- 来源发现和链接校验可共享；
- 母题使用次数、迁移记录和新标题仍按 `account_id` 隔离。

## 9. 正文规则

正文生成必须读取当前账号人设，而不是只读取业务和视角。

正文生成合同增加：

```text
account_id
profile_name
platform_account_name
business_line
perspective
identity_contract
```

身份检查必须验证正文符合当前账号人设，例如：

- 留学生本人号使用本人第一人称；
- 留学生家长号使用家长第一人称；
- 不得只因为两者都属于买家视角就判定通过。

短版和长版、选定正文、复制、发布和标签生成继续沿用现有流程。

## 10. 三日复盘规则

### 10.1 Excel归属

官方Excel来自一个具体小红书账号。

上传前页面必须显示：

```text
正在为「留学生家长号」导入三日复盘数据
绑定的小红书账号：陪娃闯秋招
```

未绑定平台账号时：

- 不允许直接完成正式导入；
- 引导先绑定平台账号；
- 或进入“历史数据人工归属”流程。

### 10.2 匹配规则

新内容：

- 只在当前 `account_id` 的正文中匹配；
- 不再遍历所有业务和视角后仅凭标题猜测归属。

历史内容：

- 可以在人工确认区跨账号搜索；
- 人工绑定后保存确定的 `account_id`；
- 不覆盖原始Excel证据。

### 10.3 学习与统计

方法胜率、有效咨询率和样本数量默认按账号人设展示。

可增加上卷汇总：

```text
账号人设
→ 视角
→ 业务
```

但账号级原始数据不得被汇总结果覆盖。

## 11. 数据模型

### 11.1 沿用现有主体

不新增与 `GrowthAccount` 重复的“子人设”实体。

允许同一组条件存在多个 `GrowthAccount`：

```text
tenant_id
owner_user_id
business_line
persona（现阶段仍表示视角）
```

### 11.2 GrowthAccount新增字段

```ts
interface GrowthAccount {
  // 现有字段继续保留
  id: string;
  tenant_id: string;
  owner_user_id?: string | null;
  business_line?: GrowthBusinessLine;
  persona: GrowthPersona;

  // 新增
  profile_name: string;
  profile_status: "active" | "archived";
  is_default_profile?: boolean;
  display_order?: number;
  last_used_at?: string;

  platform_binding?: {
    platform: "xiaohongshu";
    account_name: string;
    account_uid?: string;
    profile_url?: string;
    binding_status: "bound" | "unbound";
    bound_at?: string;
  };
}
```

说明：

- 数据库和接口中的 `persona` 暂不改名，避免破坏历史逻辑；
- 产品页面统一称其为“视角”；
- `profile_name` 才是“账号人设名称”。

### 11.3 数据库列与索引

`growth_accounts`建议增加可查询列：

```sql
business_line text
perspective text
profile_name text
profile_status text default 'active'
platform text
platform_account_uid text
last_used_at timestamptz
```

索引：

```sql
(tenant_id, owner_user_id, business_line, perspective, profile_status, last_used_at desc)
```

唯一约束：

```text
同一用户下，一个已绑定的小红书账号不能同时绑定两个激活账号人设
```

平台账号UID缺失时不强行建立唯一约束。

### 11.4 下游数据

以下现有表已经包含 `account_id`，无需重新设计父级：

- `growth_plans`
- `growth_runs`
- `content_drafts`
- `growth_reviews`

历史数据不需要重新分配，只需保留原 `account_id`。

## 12. 接口设计

### 12.1 获取账号人设摘要

```http
GET /api/growth/accounts
  ?businessLine=overseas_student
  &perspective=buyer
```

只返回摘要，不返回标题、正文和复盘大对象。

响应：

```json
{
  "accounts": [
    {
      "id": "uuid",
      "profileName": "留学生家长号",
      "oneLiner": "陪孩子走秋招的真实家长",
      "platformAccountName": "陪娃闯秋招",
      "bindingStatus": "bound",
      "isDefault": true,
      "lastUsedAt": "2026-07-30T00:00:00Z"
    }
  ]
}
```

### 12.2 创建账号人设

```http
POST /api/growth/accounts
```

必须明确：

```json
{
  "mode": "create",
  "businessLine": "overseas_student",
  "perspective": "buyer",
  "profileName": "留学生本人号"
}
```

创建接口不得再自动复用“当前视角最新账号”。

为防止断网重试重复创建，客户端提交 `idempotencyKey`。

### 12.3 更新账号人设

```http
PATCH /api/growth/accounts/:accountId
```

仅更新指定账号人设。

### 12.4 归档和恢复

```http
POST /api/growth/accounts/:accountId/archive
POST /api/growth/accounts/:accountId/restore
```

### 12.5 工作台数据

```http
GET /api/growth/bootstrap
  ?businessLine=overseas_student
  &persona=buyer
  &accountId=uuid
  &scope=core
```

当同一视角存在多个人设时，`accountId`为必填。

服务端必须验证：

```text
account.owner_user_id = 当前用户
account.business_line = 当前业务
account.persona = 当前视角
account.profile_status = active
```

管理员查看历史归档人设时允许例外，但必须显式传入管理模式。

## 13. 前端状态与缓存

### 13.1 工作空间Key

当前：

```ts
businessLine + persona
```

升级为：

```ts
businessLine + perspective + accountId
```

所有缓存、临时表单、请求取消和状态恢复必须使用新Key。

### 13.2 按需加载

为了保持当前速度优化：

1. 进入业务和视角时，只读取账号人设摘要列表；
2. 选择账号人设后，只加载该账号的 `scope=core`；
3. 进入选题后加载该账号的 `scope=content`；
4. 进入三日复盘后加载该账号的 `scope=review`；
5. 禁止预加载同一视角下所有账号人设的完整工作空间。

### 13.3 请求保护

切换账号人设时取消旧请求。

旧账号请求即使晚返回，也不得覆盖新账号页面。

每次响应必须校验：

```text
businessLine
perspective
accountId
```

## 14. 权限和安全

新增统一服务端校验函数：

```ts
requireGrowthAccountAccess({
  user,
  accountId,
  businessLine,
  perspective,
  allowArchived
})
```

所有接受 `accountId` 的写接口必须使用该校验。

禁止：

- 普通用户读取其他用户的账号人设；
- 通过修改URL把正文写入其他账号；
- 将一个业务的人设挂到另一业务；
- 将买家视角人设挂到专家或商家视角；
- 物理删除存在历史内容的账号人设。

## 15. 历史兼容与迁移

### 15.1 历史账号回填

每条现有 `GrowthAccount`：

- 保持原ID不变；
- 保持所有计划、正文和复盘关系不变；
- `profile_status = active`；
- `is_default_profile = true`；
- 根据业务和视角生成默认 `profile_name`。

示例：

| 业务 | 视角 | 默认账号人设名称 |
|---|---|---|
| 留学生 | 商家 | 求职辅导服务商号 |
| 留学生 | 买家 | 留学生家长号 |
| 留学生 | 专家 | 留学生求职老师号 |
| 中高管 | 商家 | 职业决策服务商号 |
| 中高管 | 买家 | 转型中高管号 |
| 中高管 | 专家 | 职业决策顾问号 |

### 15.2 无平台账号的历史记录

标记：

```text
binding_status = unbound
```

不影响查看、选题、正文和复制；正式Excel导入前要求补充绑定。

### 15.3 灰度兼容

迁移期间：

- 如果视角下只有一个激活账号人设，系统自动选择；
- 如果存在多个激活账号人设，要求操作者选择；
- 旧URL没有 `accountId` 时，服务端只在唯一账号场景自动兼容；
- 多账号场景不得再静默选择“最新创建的人设”。

## 17. 异常状态

| 场景 | 处理 |
|---|---|
| 当前视角没有账号人设 | 展示新建引导 |
| 账号人设未绑定小红书 | 可生产内容，不可正式导入Excel |
| 绑定账号重复 | 阻止保存并提示已有绑定人设 |
| 当前人设已归档 | 切换到默认激活人设 |
| 请求返回了旧accountId | 丢弃响应，不更新页面 |
| 切换时存在未保存修改 | 保存、放弃、取消三选一 |
| Excel账号与当前绑定不一致 | 阻止自动归入，进入人工确认 |

## 18. 测试与验收

### 18.1 多账号人设

- 留学生买家视角可以同时存在“留学生本人号”和“留学生家长号”；
- 两个人设可以分别编辑和系统生成；
- 创建第二个人设不会覆盖第一个人设；
- 刷新后恢复上次使用的人设；
- 归档后历史内容仍可查看；
- 恢复归档人设后数据完整。

### 18.2 数据隔离

- 两个人设的标题批次不同；
- A人设选择标题后，B人设不显示该选择；
- A人设正文不会出现在B人设；
- A人设发布和复盘不会进入B人设；
- 留学生本人号正文不得错误使用家长身份；
- 留学生家长号正文不得错误使用学生本人身份。

### 18.3 业务和视角隔离

- 留学生买家账号不得出现在中高管买家；
- 买家账号不得出现在专家或商家视角；
- 修改URL中的 `accountId` 不能绕过服务端校验；
- 普通用户不能读取其他用户账号。

### 18.4 选题与正文

- 13种方法适配继续按视角生效；
- 同一账号人设历史标题硬去重；
- 不同账号人设的相似标题只提示、不拦截；
- 正文生成合同包含当前 `accountId` 和人设身份；
- 短版和长版继续使用同一核心判断；
- 复制内容不带系统标注。

### 18.5 三日复盘

- Excel明确归入当前绑定账号；
- 未绑定平台账号时不能完成正式导入；
- 相同标题出现在两个账号时，不得自动错配；
- 历史未归属内容支持人工绑定；
- 复盘后方法学习只进入绑定账号。

### 18.6 性能

- 首屏不加载所有账号人设的标题和正文；
- 进入视角只请求账号摘要和当前账号核心数据；
- 进入选题只追加一次当前账号 `content` 请求；
- 进入复盘只追加一次当前账号 `review` 请求；
- 切换账号后旧请求不能覆盖新页面；
- 5个账号人设时，首屏请求数量不得线性增加。

### 18.7 历史兼容

- 现有六个业务视角工作空间均可正常打开；
- 历史标题、正文和复盘数量不变；
- 旧账号自动成为默认账号人设；
- 旧数据无需人工重新归类。

## 20. 发布策略与回滚

### 20.1 功能开关

增加：

```text
GROWTH_MULTI_ACCOUNT_PERSONA=true|false
```

关闭时恢复：

- 每个业务＋视角自动选择默认账号人设；
- 不显示多账号人设选择器；
- 历史和新数据不删除。

### 20.2 上线步骤

1. 生产数据库备份；
2. 执行兼容迁移；
3. 验证现有六个工作空间；
4. 开启管理员测试账号；
5. 创建“留学生本人号”和“留学生家长号”；
6. 走通选题、正文和复盘；
7. 灰度开放给面霸君运营；
8. 确认无串数据后全量开放。

### 20.3 回滚原则

- 回滚只关闭功能开关，不删除新增账号人设；
- 不回滚或覆盖历史 `account_id`；
- 不使用数据库硬删除；
- 不恢复“取当前视角最新账号”作为多账号场景的默认逻辑。

## 21. 默认产品决策

- “人设”统一改称“账号人设”；
- 一个账号人设首版只绑定一个小红书账号；
- 未绑定平台账号可以生成内容，但不能正式导入复盘Excel；
- 同一视角默认最多展示10个激活账号人设，更多账号使用搜索或归档管理；
- 只有一个账号人设时自动选择；
- 多个账号人设时恢复上次选择，不按创建时间自动选择；
- 账号人设只能归档，不能物理删除；
- 方法矩阵按视角共享；
- 标题、正文、发布、复盘按账号人设隔离；
- 首版不改变当前选题页面结构；
- 首版不带入 `f2b85a2` 的统一推荐标题排序功能。
